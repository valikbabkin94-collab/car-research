## Сомнительные предположения и что делает новый код

1. **Касание цены не равно исполнению.** В исходном коде populate_entry_trend проверяет последнюю закрытую свечу. WAIT всё ещё создаёт entry hint. Затем custom_entry_price для short возвращает max(proposed_rate,нижняя граница зоны), а confirm_trade_entry повторно проверяет TP1/стоп/зону и допуск. Поэтому «одна свеча дотронулась до +0,6%» нельзя считать дополнительным реальным входом; также нельзя трактовать WAIT как гарантированное отсутствие заявки.
2. Исследовательский replay берёт только завершённую предыдущую1m-свечу. Сигнал становится доступным не раньше first_received; первая полная минутная граница после получения — первое решение. После проверки TP1/SL формируется лимит max(open,zone_low), живущий одну минуту; вышеzone_high — WAIT. Зона от planned limit×0,999 до×1,003. Эти правила не выданы за точный реальный Freqtrade: реальные bid/ask, latency, callback scheduler, order timeout и config-overrides отсутствуют.
3. Сначала проверяется завершённая цена: TP1 уже пройден/стоп уже пройден → не открывать. Плановый TP до принятия заявки не превращается в прибыль; свеча до приёма заявки не может её исполнить. Бар, который может сначала достичьTP1, а затем лимита, помечается неоднозначным.
4. При SL и TP в одной минуте — SL первым; gap short-stop — max(open,stop). Прибыльный TP в минуте входа запрещён. BE послеTP1 действует только со следующей минуты. Доли50/30/20 сохраняются, сумма закрытых долей=1. Это консервативные соглашения, не гарантированная математическая нижняя граница тиковой истории.
5. Все стопы/TP привязаны к модельному исполнению; проценты5,6/2,1/4,2/6,3 и BE0,9989 неизменны. Hold72h — исследовательский cap старой модели, фактический runtime нужно сверить. TTL в новом протоколе отсчитывается отfirst_received; его совпадение с исходными created/expires необходимо подтвердить при получении архива.
6. Расходы21/35/50bp — полный round-trip budget (комиссии+условное проскальзывание), без двойного вычитания. Первичный1R=5,6% entry. Совместимый старый0,0581 выводится в другом поле и не смешивается. Пока нет funding/марок/исполнений, **true_net_R=null**, а price_R — только ценовая модель после бюджета расходов. Funding не заменяется нулём. Текущий код не рассчитывает funding cash: это явное незавершённое место до появления архива и отдельного валидированного входного формата ставок/марок.
7. Модель не подменяет наблюдаемый timestamp ордера временем начала свечи: actual_fill_verified всегдаfalse. Снимки допуска имеют asof, наблюдения из будущего или старше1min не принимаются. BLOCKED и UNKNOWN показаны отдельно. Даже полный observed gates-pass в A не доказывает причинную реализуемость C: C может занять другие слоты и изменить последующую доступность портфеля.

## Зафиксированная независимая paper-проверка

Первичный forward — только A/C, без переобучения top50, изменений стопов/TP/долей/риска. B нужен только для воспроизведения старого сравнения, не для последующего выбора по новой выборке. Регистрация времени уже сохранена; исходный signal_ms И first_received должны быть строго позже неё. Старые65 никогда не считаются независимым OOS.

До начала первичного cohort требуется hash исходной top50-модели и снимок правил допуска. REGISTRATION.json сейчас model_snapshot_verified=false, поэтому forward-CLI намеренно отказывается считать модель как новую подтверждённую выборку. После независимого ревью нужно отдельным регистрационным коммитом зафиксировать исходный model hash и новый фактический старт сбора. Не активировать существующие процессы и не менять стратегию ради этого.

Manual ingest создаёт хеш-цепочку, не перезаписывает старый пакет, отделяет старые сигналы, конфликтующие дубликаты отвергает. First_received остаётся заявлением исходного журнала, а не доказанным GitHub временем получения; для независимой проверки нужны append-only журнал и timestamp публикации пакетного commit. Поздние/восстановленные строки не превращаются в проспективные автоматически.

Все возможности A/C учитываются попарно, включая окончательные непринятия. Неисполнение=0 только при полностью наблюдённом окончательном исходе; PENDING/DATA_GAP не ноль. Основное сравнение — R/возможность и календарную неделю, отдельно R/сделку, PF, drawdown, серии убытков и концентрация по монетам/дням. Для истинного net потребуются funding и достоверные исполнения; пока эти метрики НЕ ПРОВЕРЕНО.

Порог оценки заранее: минимум8полных недель и100новых закрытых независимо допустимых paper-сделок в каждом A/C; раньшеINCONCLUSIVE, без остановки после удачного дня. Отдельно минимальный порог владельца100новых shadow и>0,1R/сделку. Для предпочтенияC нужны положительный результат после50bp, положительный парный эффект надA с week-block bootstrap95% нижней границей>0 и устойчивость без лучших3монет/дней.10 000bootstrap, seed20261121. Этот статистический модуль/портфельное проигрывание ещё НЕ РЕАЛИЗОВАНЫ: данных нет, и статистическая проверка не выполнялась. Последующий код должен соблюдать уже замороженную методику и пройти независимый review до нового PnL.

BTC-режим: последняя уже закрытая минута против закрытия24hназад, DOWN≤−3%, UP≥+3%, иначеSIDEWAYS; нет timestamps/цен — UNKNOWN. Группыn<40 — мало данных. Даже прохождение paper-порога не даёт автоматического разрешения LIVE.
